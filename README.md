# Склад / Учёт — система управления инвентарём для розничного магазина

Приложение по варианту «Система управления инвентарём для розничных магазинов»
(лабораторная работа №1, объектное моделирование интеллектуальных систем).

Внешний вид соответствует скриншотам из методички: тёмная боковая панель, верхняя
строка с хлебными крошками и выбором сотрудника, страницы «Главная», «Товары и
остатки», «Приёмка товара», «Продажа товара», «Возврат товара», «Инвентаризация».

## Возможности

- Каталог товаров: поиск по названию/артикулу, фильтр по категории, добавление и редактирование товара.
- Приёмка товара: выбор поставщика и документа, добавление строк поступления, сохранение увеличивает складские остатки.
- Продажа: выбор доступного товара, списание сначала с торгового зала, затем со склада; при падении остатка ниже порога создаётся задача на пополнение полки либо заявка на дозаказ поставщику.
- Возврат: поиск продажи по номеру документа, возврат позиции с проверкой количества и обязательной причиной; остаток возвращается в торговый зал.
- Инвентаризация: сверка фактического количества с учётным (все места / основной склад / торговый зал), сохранение результатов, недостачи оформляются актом списания.

## Технологии

- Python 3
- PyQt6 — интерфейс
- SQLite — хранение данных в файле `inventory.db` (создаётся автоматически)
- SOLID: доменные модели в `src/models.py`, сервисный слой в `src/service.py`,
  доступ к БД в `src/database.py`, виджеты/страницы в `src/pages/`, общий вид в `src/common.py`.

## Запуск

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python3 src/main.py
```

Если PyQt6 уже установлен системно, достаточно:

```bash
python3 src/main.py
```

База данных `inventory.db` создаётся рядом с проектом при первом запуске и
заполняется демонстрационными товарами, поставщиками и сотрудниками.
Демо-доступы (пароль `123`): `manager`, `storekeeper`, `cashier`.
Для чистого старта удалите `inventory.db`.

## Структура

```text
src/main.py          точка входа: классы RetailInventoryApp и ApplicationInitializer
src/main_window.py   главное окно, боковая панель, верхняя панель, класс InventoryUI
src/common.py        общий стиль и вспомогательные виджеты (функции, классов нет)
src/service.py       InventoryService и роли сотрудников (Manager, WarehouseKeeper, Cashier)
src/database.py      схема SQLite, начальные данные, репозиторные операции
src/models.py        доменные модели предметной области
src/pages/           страницы приложения
tests/               unittest-проверки бизнес-логики (тесты идут через Database)
```

## Классы, которых нет на диаграмме, и почему они добавлены

На UML-диаграмме из отчёта предметная область показана укрупнённо. Ниже — все
классы, которые есть в коде, но отсутствуют на рисунке, с обоснованием. Их можно
разбить на три группы: предметная область, интерфейс и хранение данных.

### 1. Предметная область (`src/models.py`)

| Класс | Почему добавлен |
|---|---|
| `Employee` | На диаграмме роли (`Manager`, `WarehouseKeeper`, `Cashier`) показаны отдельными классами с одинаковым набором атрибутов (`employee_id`) и отношением *uses* к `InventoryUI`. Чтобы не дублировать код трижды, в коде они сделаны наследниками базового класса `Employee` (единая таблица `employees`, единая аутентификация), а три UML-класса сохранены как подклассы со своими операциями из диаграммы. |
| `Category` | Диаграмма не моделирует категории, но текст задания требует: «Управляющий запускает инвентаризацию для выбранной категории товаров», а каталог фильтруется по категории. Так же хранится категория товара на складе (таблица `categories`). |
| `Location` | В тексте два места хранения — «на складе» и «на торговом зале» (сценарии приёмки и продажи). В UML это отражено только строкой `location_type: str` у `InventoryBalance`; в коде места хранения — справочник `locations` (kind: `warehouse` / `shelf`), чтобы остатки по полке и складу хранились раздельно, как в обязательных сценариях. |
| `Stock` | Сводная строка по товару: сколько на складе, сколько на полке, порог полки. Нужна страницам «Товары и остатки» и «Продажа» (отображать и искать доступные товары) и подсистеме аналитики из текста задания («рассчитывает нераспроданные остатки товара»). Операция `check_stock(product_id): int` в UML возвращает голое число — для экрана этого мало, поэтому в коде она опирается на полноценную сводку. Товар из диаграммы (`Product`) при этом не «замусорен» полями остатков. |
| `GoodsReceiptLine` | На диаграмме это просто связь *GoodsReceipt — 1..\* — Product*, но по сценарию приёмки кладовщик фиксирует «фактическое количество каждого товара». Позиция поступления (товар + количество) моделируется строкой — это класс-ассоциация, отображаемый в таблицу `receipt_items`. |
| `SaleLine` | Аналогично для продажи: строка продажи несёт количество и цену (таблица `sale_items`), из позиций рассчитывается `total_amount` продажи. Связь *Sale — Product* на UML без количества и цены реализовать невозможно: продать «товар вообще» нельзя. |
| `ShelfTask` | Сценарий №2 прямо требует: «система создаёт задачу для кладовщика на пополнение полки со склада». На диаграмме есть только операция `create_replenishment_task()`, но нет класса, где хранится сама задача. Добавлен как `<<data>>`-класс (таблица `shelf_tasks`) со статусом (`new`/`done`). |
| `WriteOffAct` | Сценарий №3: «управляющий принимает решение о списании недостач…», недостача «оформляется актом списания»; в UML есть операция `record_discrepancy()`, но нет класса-результата. Акт на списание хранится в таблице `writeoff_acts` и создаётся как автоматически (по инвентаризации), так и через `InventoryService.record_discrepancy()`. |

### 2. Интерфейс (`src/main_window.py`, `src/pages/`, `src/login_dialog.py`)

| Класс | Почему добавлен |
|---|---|
| `MainWindow` | Конкретная реализация границы `InventoryUI` в Qt: центральное окно со стеком страниц. На диаграмме `InventoryUI` — один класс-граница; в коде PyQt требует окно-контейнер. Именно `InventoryUI` (фасад) изолирует приложение от деталей Qt, отношения *uses* из диаграммы сохранены. |
| `TopBar` | Верхняя панель с хлебными крошками и выбором сотрудника — по обязательным скриншотам интерфейса из методички. Часть UI-границы, на класс-диаграмму не вынесена. |
| `Sidebar` | Тёмная боковая панель навигации по операциям. Отвечает за доступность страниц по роли (управляющий/кладовщик/кассир выполняют только свои операции). |
| `HomePage` | Страница «Главная» с карточками операций — реализует операцию `show_main_menu()` из диаграммы. |
| `GoodsPage` | Страница «Товары и остатки» — реализует `handle_reports()` (просмотр остатков по товарам, подсистема аналитики из текста) и часть сценария приёмки — ведение справочника товаров. |
| `ProductDialog` | Диалог добавления/редактирования товара — редактирование данных класса `Product`. |
| `ReceiptPage` | Страница «Приёмка товара» — реализует `handle_goods_receipt()` и сценарий №1 (сверка с накладной, ввод фактического количества). |
| `SalePage` | Страница «Продажа товара» — реализует `handle_sale()` и сценарий №2 (списание с полки, автоматические задачи/заявки). |
| `ReturnPage` | Страница «Возврат товара» — реализует `handle_return()` (поиск продажи по документу, причина возврата обязательна). |
| `InventoryPage` | Страница «Инвентаризация» — реализует `handle_inventory()` и сценарий №3 (сверка факта с учётом по категории/месту, отчёт о недостачах и излишках). |
| `LoginDialog` | Диалог входа в систему. В UML вход показан только атрибутом `current_user_id` у `InventoryUI`, но сценарии выполняются конкретными сотрудниками (управляющий, кладовщик, кассир), поэтому нужен экран входа с проверкой логина/пароля и передачей роли в `InventoryUI`. |

### 3. Хранение данных (`src/database.py`)

| Класс | Почему добавлен |
|---|---|
| `Database` | Слой доступа к данным (репозиторий). Методичка требует хранить сведения в SQLite («хранится в отдельном файле и не требует установки сервера»), а UML-диаграмма хранение не моделирует. Выделено в отдельный класс по принципу единственной ответственности: `InventoryService` занят бизнес-правилами (пороги полки, задачи, заявки), а SQL-схема, начальные данные и транзакции — здесь. Благодаря этому тесты бизнес-логики (`tests/test_database.py`) работают напрямую с `Database` и не требуют графического интерфейса. |
| `CategoryRow` | Вспомогательная мелкая обёртка пары (id, name) для списка категорий в комбобоксах. Не доменный класс, просто удобный доступ к полям строки SQLite. |

> Не перечислены как классы: функции-хелперы (`make_button`, `make_table`,
> `apply_app_style`, `format_qty` и т.п. в `src/common.py`) — они стилизуют
> виджеты и не являются объектами предметной области, а также фабрика
> `make_role()` в `src/service.py`, которая строит нужный ролевой класс
> (`Manager`/`WarehouseKeeper`/`Cashier`) из сотрудника.

## Права доступа по ролям

Дизайн и поведение страниц воспроизводят скриншоты из отчёта (рисунки 9–14),
расположение и названия кнопок сохранены. Страницы ограничивают видимость и
действия по роли, как в UML (отношение *uses* каждой роли к `InventoryUI`):
кладовщик не видит продажи и возвраты, кассир — приёмку и инвентаризацию,
управляющий видит всё.
